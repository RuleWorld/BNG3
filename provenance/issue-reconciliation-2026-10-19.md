  independently constructed instance reproduces the same seed.
- `lifecycle-independent-caches` — one instance mutated while its sibling keeps its own
  parameter values and its own generated-network object.
- `lifecycle-independent-solver-state` — repeated, early-stopped and interleaved
  stochastic runs on one instance leave the deterministic trajectory unchanged.
- `lifecycle-exception-cleanup` — a stop-condition failure raised after the solver
  allocated its state leaves the instance usable and every recovered trajectory equal
  to a fresh compilation.
- `lifecycle-parameter-only-reuse` — a rate-parameter override preserves the compiled
  structure and reproduces a fresh compilation and the closed-form law.
- `lifecycle-topology-invalidation` — a topology-changing `include_model` action
  invalidates the cached network; the rebuilt trajectory equals a fresh compilation of
  the merged source and the closed-form chain law.
- `lifecycle-compartment-invalidation` — a `setVolume` action invalidates reuse; the
  rebuilt trajectory equals a fresh compilation with the new volume and the closed-form
  volume law.

The topology and compartment checks exposed a product defect: `BioNetGenModel.execute()`
applied the model's actions to the compiled model but left the cached generated network
in place, so an action that changed the model was followed by a simulation of the old
network. `python/bionetgen/model.py` now discards the cached network when the action
block runs, in a `finally` clause so a failed action cannot leave a stale cache either.
The regressions are `tests/python/test_model_reuse_contract.py::test_action_execution_invalidates_the_cached_generated_network`
and `::test_volume_action_invalidates_the_cached_generated_network`; both fail against
the unrepaired model and pass against the repaired one.

The catalog's nine #141 obligations now name these checks instead of the
`qualification:issue:141:*` placeholders, and their scope boundaries and feature
combinations are declared. Runtime topology editing through the public `Model` API
remains unsupported and stays an explicit boundary. The governance obligations
(`implementation-or-disposition`, `exact-revision`, `validation-receipt`,
`remaining-limits`) keep their disposition checks and are still open, so the issue
stays open.

### Export contract scope

`bngir-export:v02-site-bearing-roundtrip` exercises the site-bearing v0.2 envelope through
the native reader and writer, and `bngir-export:v02-site-bearing-python-roundtrip` exercises
the same envelope through the Python reader and writer. Both reproduce the retained document
exactly. The site-free envelope has its own contract, `bngir-export:v02-independent-roundtrip`,
so the two envelopes stay separately visible.

### JAX backend on an accelerator

The CI job for the JAX backend pins `JAX_PLATFORMS: cpu` so its result is deterministic
and independent of the accelerator a runner happens to have. The same suites were run
locally on the Apple Metal device of this machine, which the CI job cannot reach:

- `JAX_ENABLE_X64=false` with the default Metal device: `tests/python/test_jax_ode.py` and
  `tests/python/test_jax_ssa.py`, 25 passed.
- `JAX_ENABLE_X64=true` with the default Metal device: `tests/python/test_jax_ode.py`, 20
  passed.

The device is reported by JAX as `METAL`; the lower-case spelling `metal` is rejected by
JAX's own backend list, so an accelerator run must use the name JAX reports. This is
supplementary device-diversity evidence for the JAX backend, not a replacement for the
CPU-pinned gate.
